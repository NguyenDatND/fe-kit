# Accessibility

Defaults for repos that do not say otherwise. The project's own standards win where they differ. What the linter's accessibility rules already catch is not repeated here.

## Structure and names
- Use the element that matches the job: `button` for an action, `a` for navigation, `ul` for a list, headings in order, landmarks (`main`, `nav`) for regions. A clickable `div` needs a role, `tabIndex`, key handling and a name; usually the answer is a `button`.
- Every interactive control has an accessible name: its visible text or label first, `aria-label` only when there is no visible text. Link text says where it goes ("Download invoice", not "click here").
- Images carry `alt` that says what they convey; decorative ones get `alt=""`. Icon-only buttons get a name.
- Reach for ARIA only to fill a gap that HTML cannot. Never put `aria-hidden` on something focusable.

## Forms
- Every field has a `label` tied to it (`htmlFor`, or wrapping the input). A placeholder is not a label.
- Show an error next to its field, link it with `aria-describedby`, and mark the field `aria-invalid`. Do not rely on colour alone to say something is wrong or required.
- Announce results that appear without a page change (saved, failed, loading) with a live region (`role="status"` or `role="alert"`).

## Keyboard and focus
- Everything that can be done with a pointer can be done with the keyboard, in a sensible order. Never use a positive `tabIndex`.
- Keep a visible focus indicator; do not remove the outline without a replacement.
- A dialog moves focus into itself, keeps it there while open, closes on Escape, and returns focus to what opened it. After a route change, move focus to the new page's heading or main region.

## Appearance
- Text contrast is at least 4.5:1 (3:1 for large text and for the borders of controls).
- Respect `prefers-reduced-motion` for animation, and do not block zoom or text resizing.
